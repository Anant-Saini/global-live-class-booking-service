# Project Overview: Global Live-Learning Booking System

## Purpose
This document serves as a high-level technical specification and alignment guide for the development of the Global Live Class Offering Booking System. The goal is to provide a production-ready backend service that manages global class schedules, handles complex timezone conversions, and ensures data consistency during concurrent booking attempts.

## Core Domain Entities
1.  **Course/Class**: The base template for learning content (e.g., "Python Coding").
2.  **Offering / Section**: A specific schedulable instance of a Course (e.g., "Saturday Batch").
3.  **Session**: The actual meeting occurrences within an offering, defined by specific start and end times.
4.  **User**: Divided into two primary roles:
    *   **Teacher**: Creates offerings and manages schedules.
    *   **Parent/Student**: Views and books offerings.

## Key Functional Requirements

### Teacher Workflow
*   **Create Offering**: Define the metadata for a course section.
*   **Session Management**: Add specific time slots to an offering.
*   **Visibility**: View self-created upcoming offerings and their constituent sessions.

### Parent Workflow
*   **Discovery**: View available offerings with session times localized to the Parent's timezone.
*   **Booking**: Book an entire offering (all sessions inclusive).
*   **Portfolio**: View a history/list of booked offerings.

## Critical Business Rules

### 1. Atomic Offering Booking
Booking is strictly at the **Offering level**. A parent cannot book individual sessions; they must commit to the entire batch.

### 2. Timezone Integrity
*   **Teachers** create schedules in their local timezone.
*   **Parents** must see session timings converted to their own local timezone.
*   **System** should ideally store timestamps in UTC to ensure global consistency.

### 3. Conflict Detection & Locking
Once a parent books an offering, they are "locked" for those specific time windows. 
*   **Validation**: The system must prevent a parent from booking another offering if *any* session in the new offering overlaps with a session in an already booked offering.

### 4. Concurrency Handling
The system must remain robust under high load:
*   Handle multiple parents attempting to book the same offering simultaneously (Race conditions on `bookedSeats`).
*   Prevent a single parent from double-booking overlapping slots via rapid, simultaneous requests.

## Technical Stack Requirements
*   **Language/Framework**: Java + Spring Boot.
*   **Database**: PostgreSQL or MySQL (Relational DB is preferred for ACID compliance).
*   **Design Patterns**: Clean architecture, thoughtful error handling, and scalable database design.

## Engineering Goals & Evaluation Criteria
*   **API Correctness**: Strict adherence to the RESTful patterns.
*   **Database Design**: Efficient indexing and normalization to support conflict detection queries.
*   **Timezone Logic**: Robust handling of offsets and DST.
*   **Conflict Detection Logic**: High-performance overlap checks.
*   **Data Consistency**: Use of transactions and locking mechanisms (Pessimistic/Optimistic) where appropriate.
